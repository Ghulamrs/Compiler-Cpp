## The register: seven programs, each a known wrong answer

`tests/open` gates nothing on purpose, and each entry is a program with
clang's answer beside it. Two arrived from the last rounds:

  - **virtual-base-second-base** - a second base with a virtual base of its
    own is read through the wrong pointer on the Itanium targets.
    x86_64-windows gets it right, and the note says why.
  - **virtual-dtor-through-virtual-base** - `delete` through a pointer to a
    polymorphic *virtual* base never reaches the most-derived destructor, on
    **both** ABIs, which is what says the fault is in how the destructor slot
    is found rather than in either layout.

The five older ones are catch-copy-throws, constexpr-double,
lambda-class-scope-names, lambda-return-through-try and
mem-init-template-id-base. `tests/open/README` has the rules a new entry must
meet and what closing one requires.

## Recorded differences that are not defects in the register

Three markers carry the rest, and each names its reason in prose beside the
case: **19 `.notarget`** files (a target refuses the shape, x86_64-windows in
every case), **74 `.nocl`** (a name cxx1 emits and `cl` does not, or the
reverse), **132 `.nonames`** (the same against clang). They are worth reading
as a list of what to do next, and three groups stand out:

  - **Windows exceptions.** A destructible local beside a `try`, a `return`
    out of a handler, a `try` inside another, a class-typed `throw`, a rethrow
    from inside a handler. All are the FH3 funclet model, none of it is the
    Itanium call-site list, and rung 6.5 records the lag.
  - **The Microsoft RTTI for a base that is not at offset 0.** cxx1 emits a
    complete-object locator where cl and clang emit a base-class descriptor
    carrying the offset. Nothing reads it today on that target - a class-typed
    throw is refused and an upcast is static - so it is a name difference now
    and a wrong answer the day a `dynamic_cast` needs it.
  - **The VTT and the construction vtables** on Itanium, which clang emits and
    cxx1 does not. Nothing wants them until a virtual function is called from
    inside a base constructor, and that shape is refused rather than guessed.

## Two things to check before trusting a green suite

**A golden that does not move is not proof the code is unreachable.** The
own-vptr defect - a class introducing a vptr over a plain base, which
segfaulted - changed **no** existing golden file when it was fixed, because in
460 cases no test had that shape. A green suite says what it ran, not what it
covers.

**A subagent's numbers need re-measuring, and not in its tree.** The
primary-base round was written by a Fable 5.1 subagent in its own worktree and
every number was re-taken here before it landed. Running a suite in an agent's
worktree while the agent is running one collides in `tests/out-run` and
invents failures on unrelated cases; that cost a wrong report of a
`named-casts` failure that never existed.

## The comment-line policy

Instructed and applied on 2026-09-11: three lines to a comment group, one line
where a single line of code follows. `tools/comment-lines` is the oracle and
`make comments` names every breach. The sweep took about 3,000 comment lines
out of `src/`; forty single-line comments still run past 100 columns, which the
policy permits and which is the residue a hand would tidy. CLAUDE.md's section
of the same name carries the rest, including what the sweep had to be taught.
