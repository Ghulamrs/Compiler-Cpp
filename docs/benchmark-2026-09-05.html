Sixteen Sources, Three Machines

How long cxx1 takes to compile Compiler++ against the compiler each platform ships with — and where its own time actually goes.

What was compiled. The sixteen .cpp files of Compiler++, a separate C++98 compiler of about 12,000 lines that cxx1 now builds correctly on macOS and x86_64-linux. Every run produces sixteen object files from cold sources; nothing is linked, because linking would time the platform's linker rather than either compiler.

What the native compiler was asked for. -O0, or /Od for cl. cxx1 has no optimiser at all, so -O2 would be timing a pass it does not run. This is a measurement of time-to-working-code on one real program, not a like-for-like comparison of two compilers doing the same work — clang, g++ and cl are each carrying an optimiser, a diagnostic engine and a debug-info writer that cxx1 has no equivalent of.

cxx1 wins every comparison here, serial and parallel, on all three machines. It did not when this page was first written: the parallel column was a loss on two of them, and the next two sections are the two things that had to change — one in the compiler, one underneath it.

-j parallelises compilation and not assembly. Driver::assembleObjects in src/Driver.cpp is a plain serial loop that spawns one assembler per file. On the Mac the compile phase falls from 0.27s to 0.08s under -j12 — a clean 3.4× — and then the twelve megabytes of assembly it produced take 1.94 seconds to assemble, whatever -j says.

Process spawning is not the cost. Sixteen invocations of c++ -c on a four-line .s file take 0.37s on the Mac, so the other 1.5 seconds is the assembler doing real work on real input.

One: the assembler is a job like any other

Driver::assembleObjects was a plain serial loop spawning one assembler per file, so sixteen sources compiled in 0.08s on twelve cores and then took 1.9s to assemble one at a time. It runs on the same work-stealing pool the compiling does, and so does the Windows link path, which had its own copy of the loop.

Windows took that whole: 0.75s to 0.29s. The Xeon took what it had — its two vCPUs are hyperthread siblings of one physical core, and g++ itself gets only 1.16× from the second, so 1.28 to 1.20 is the machine's ceiling rather than a shortfall. The Mac did not move at all.

Two: system() is not a way to start a process

-time said “16 tool runs on 12 threads” and the wall clock stayed at 1.98s, because Apple's libc holds a global lock for the duration of the child. Concurrent std::system calls serialise completely. The same question put to all three C libraries:

posix_spawn and waitpid in place of std::system on the POSIX path took the Mac from 1.98s to 0.50s, which is the 0.08 of compiling plus 0.42 of assembling — within a hair of the 0.45s the same files took through xargs -P12, which is what said the ceiling was the library and not the work.

Asking all three was the point. The first machine measured is the one that behaves differently from the other two, and a conclusion drawn from it alone — that parallel assembly does not help — would have been wrong about two platforms and wrong about the cause on the third.

The pool also closed a data race it would otherwise have opened: the command named in an assembler error was one file-scope string that several threads would have written at once. It is per-thread now, and the first failure by index is reported rather than whichever thread lost the race, so a rerun blames the same file.

The compiler proper

Compile-only, stopping at assembly, so the platform assembler is out of both sides. Measured on the Mac; the other two machines were not asked for assembly-only output.

cxx1's front end and code generator get through these sixteen files about fifteen times faster than clang's. That is doing full C++ parsing, name lookup, overload resolution, template instantiation by token replay, and mangling for both the Itanium and Microsoft ABIs — but no optimisation, no debug info unless asked, and a diagnostic engine that stops at the first error.

Read the ratio as the cost of everything clang does that cxx1 does not, more than as a verdict on either. The useful figure for a person waiting on a build is the source-to-object one above.

What this is not

Not a scaling study. The three machines are wildly unlike: 12 fast cores against 2 slow ones on 419 MB against 20 threads on 64 GB. The Xeon's 1.16× from a second core is a memory ceiling, not a parallelism result — g++ will not fit twice in that box.

Not a quality comparison. The native compilers produce optimisable IR, full debug information and far better diagnostics. cxx1 produces working code for one program.

Not one snapshot. The source-to-object figures are cxx1 as it stands after the parallel assemble step; the “was” markers show where each machine started. The std::system table is a property of each platform's C library, not of cxx1.

Not the whole build. Linking is excluded, and on Windows cxx1 cannot link Compiler++ at all yet — ml64 has no COMDAT directive, so every inline and template member collides. Compilation and assembly are what is measured here, and both succeed on all three.
