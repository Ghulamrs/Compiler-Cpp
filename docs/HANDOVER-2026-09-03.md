# The claim, the comparison, and a ladder to compiling Compiler++

Written as the session ended. `docs/HANDOVER-2026-09-02.md` is the previous
round and stays as written; this file supersedes its "What is open" list.
`main` is at `22b445a`, one commit ahead of where this round found it.

## What landed

**`22b445a` — `docs/EXCLUSIONS.md`, `tools/exclusions`, and a corrected
CLAUDE.md.** The first sentence of `CLAUDE.md` said "the language `cxx1`
compiles is C++11", which is a claim this compiler cannot support:
`dynamic_cast` is refused, conversion functions do not exist, and `lib/` is
sixteen **C** headers. It now reads "C++11 — minus the list in
`docs/EXCLUSIONS.md`, and with no C++ standard library at all", with a
paragraph under it saying that an ordinary conforming C++98 program does not
compile here.

`docs/EXCLUSIONS.md` is that list: **103 refusal sites, 95 distinct messages**
at the commit it was taken, each cited by `file:line` and grouped by subject,
the standard library named first because it is the largest exclusion and is not
a language feature at all. It is derived rather than written: `tools/exclusions`
takes the inventory out of the source and `--check` reports every refusal the
document does not cite and every citation whose site is gone. It reads
`103 sites, 0 uncited, 0 stale citations`.

**A rule came with it, and it is the one to keep:** when a feature lands,
delete its entry from `docs/EXCLUSIONS.md` and run
`tools/exclusions --check docs/EXCLUSIONS.md` **in the same commit**. A refusal
that names a feature the compiler now has is a claim the compiler cannot
support, which is the same defect as the headline this round fixed, one level
down.

**One grep cannot derive the list, and that is worth fixing.** The messages are
written three ways — "is not supported yet", "is C++14, and this compiler is
C++11", and eleven that carry neither and say only "yet". `dynamic_cast`'s
message is in the third group, so the most consequential exclusion in the
compiler is the one a naive grep misses. The house phrasing to adopt: a new
refusal says "is not supported yet" or names a standard version. Until every
message does, `tools/exclusions` is the derivation and a grep is not.

## What a review of this tree found, and what is open

`docs/COMPARISON-2026-09-03.md` is this tree read against `Compiler++` by three
Fable reviewers; the two half-reviews it quotes are not in the repository. Five
silent wrong answers in ordinary C++11 came out of ~70 probe programs, none
visible to any suite. **They are open.** In severity order:

1. **A crash.** Copying a 1/2/4-byte `const` class object segfaults.
   `Parser::convert` (`src/parser/ParserOverload.cpp:53`) builds a `Cast`
   between `const P` and `P`, and every backend's `genConversion` truncates the
   address to the object's size. Confirmed by patch.
2. **A user-written destructor never destroys class-typed members.**
   `synthesizeDestructor` is the only place that does it; the written path in
   `ParserStmt.cpp` appends base calls and nothing else.
3. **A class returned by value and used as an operand, a condition, or
   discarded is never destroyed.** `completeCall`
   (`src/parser/ParserExprCall.cpp:275`) allocates the slot and never pushes it
   to `pendingTemps_`.
4. **A downcast from a non-first base pointer does not subtract the offset** —
   `convert` handles only upcasts.
5. **A call returning `T &&` is treated as an lvalue**, so it copies where
   clang moves and `f(S &&)` is never chosen (`useReference`,
   `src/parser/ParserExpr.cpp:1068`). Confirmed by patch.

**Nine of the ten silent findings across both trees are the same shape**: a rule
written for one of two symmetric paths, pinned by a regression case for *that*
path, and never applied to its twin — implicit destructor but not written,
copy-construct but not copy-assign, direct cast but not returned reference. The
review's own words: a case written to prove a fix proves that fix. `CLAUDE.md`
has the rule for this already (an invariant a person has to remember is a defect
with a delay on it); it is not yet applied where the lifetime rules live.

**The instrument that would see this class of bug does not exist here.** The
recommendation, with evidence behind it, is a lifetime-balance case family: one
`live` counter incremented in every constructor, decremented in every
destructor, printed after each shape and asserted back to zero. `by-value.cpp`
declines to count *constructions* because clang and cl disagree about elision,
and that objection is correct — but a **balance** is elision-invariant, since
whatever is elided loses its construction and its destruction together. Three of
the five findings above show as a nonzero line. This is the cheapest instrument
that sees what the tree actually leaks.

Also negative, and worth not re-deriving: cross-target integer folding (10/10
against clang on both non-host targets), the arm64 ABI re-measured by
cross-linking twelve aggregate shapes in all four caller/callee pairings, ~45
arithmetic and conversion shapes, exceptions across frames, and overload
ranking — all agree. **Three items the 09-02 handover lists as open are fixed**:
an unnamed member built by a written constructor, the `f(int)` /
`f(const int &)` ambiguity, and `goto` past a destructor.

## The programme: making cxx1 compile Compiler++

The goal set this round is that **cxx1 compiles the Compiler++ tree without
Compiler++ being touched**. It is a real target rather than a curiosity, because
of one measurement:

**Compiler++ is a strictly conforming ISO C++11 program.**
`clang++ -x c++ -std=c++11 -pedantic-errors -fsyntax-only` over all 32 sources
gives **0 errors and 0 warnings**. The only non-ISO code sits behind two
platform guards a cxx1 build would never take — `__int64` under `_MSC_VER`
(`Bytecode.h:40-42`) and `<io.h>`/`<fcntl.h>` under `_WIN32`
(`main.cpp:58-60`) — and the `long long` that makes it fail a *C++98* pedantic
check is standard C++11. So a complete C++11 implementation must compile it, and
the whole of the gap is this compiler's.

The shape of the gap is smaller than it looks. Compiler++ is C++98, so **none of
cxx1's C++11-only machinery is needed** — no lambdas, `auto`, move, range-for,
`noexcept`, variadic templates. It **defines zero templates of its own**, so
every template exclusion matters only for the library. It uses **no `friend`
declarations, no virtual bases, no conversion functions, and no catch-by-
reference**. Four walls, and a library:

| wall | sites in Compiler++ | refused at |
| --- | --- | --- |
| `dynamic_cast` | **354** | `src/parser/ParserExpr.cpp:478` |
| static member functions | **27** | `src/parser/ParserType.cpp:523` |
| unnamed namespaces | **7** | `src/parser/ParserStmt.cpp:1599` |
| using-declarations | **6** | `src/parser/ParserStmt.cpp:1632` |

The 354 `dynamic_cast`s are not incidental: `cc::ASTNode` (`AST.h:60`) carries
no kind tag, and that file's own layering comment says the semantic pass "walks
the tree and uses `dynamic_cast`". It is the dispatch mechanism of the two-layer
design.

**The include-path mechanism already exists** — the driver takes `-I` at
`src/Driver.cpp:383` — so `include/` needs populating, not inventing.

### The ladder, and why the order is this order

1. **using-declarations, static member functions, unnamed namespaces.** Needed
   by Compiler++'s own source; and the first is needed by the library's *first
   header*, because `<cstddef>`'s natural spelling is
   `namespace std { using ::size_t; }`.
2. **The lifetime seam** — findings 1, 2 and 3 above, with the balance case
   family that catches them. Before containers, not after.
3. **RTTI and `dynamic_cast`.** A `type_info` beside every vtable, the
   inheritance graph it carries, and the `__cxa_` call that walks it, on two
   ABIs. The Itanium vtable already has the typeinfo slot, holding a plain
   zero, so the shape exists and wants filling.
4. **The library**, under `include/`: `<cstddef>`, `<cstdlib>`, `<cstring>`,
   `<cmath>`, `<cctype>` as thin wrappers over `lib/`, then `string`, `vector`,
   `map`, `set`, `ostream`, `ostringstream`, `iostream`, `algorithm`,
   `fstream` — only as much of each as Compiler++ actually calls.
5. **Link and run** the whole tree, and diff its six suites against the ones a
   host-compiled Compiler++ produces. That last step is the real oracle: the
   two binaries must agree, case for case.

**Rung 4 cannot be swapped in front of rung 2.** A container library is
entirely copy constructors, destructors and returned temporaries — exactly the
seam where findings 1–3 live — so writing it first means debugging the library
against a compiler that miscompiles it, with no way to tell which is wrong.

**A caveat about scope that the next session should hold on to.** Finishing this
ladder makes cxx1 compile *this program*. It does not make cxx1 a conforming
C++11 implementation, and `docs/EXCLUSIONS.md` will still have most of its
entries afterwards. Those are different goals and only one of them is on the
table.
