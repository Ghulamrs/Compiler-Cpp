# Where this round stopped: one miscompilation, narrowed to a call site

Compiler++ — a separate tree at `~/Documents/Claude/Compiler++`, **never
modified by this work** — is the exercise cxx1 has been measured against.
Where it stands:

    16 of 16 sources        compile
    16 of 16 objects        assemble
    1 of 1 program          links, runs, prints its usage
    128 of 129 test cases   byte-identical output to a clang build of the
                            same sources with the same headers

The one that differs is `tests/cases/14_virtual_override.cpp`, and this file
is the record of how far it was narrowed and by what, so the next round starts
from the evidence rather than from the beginning.

## The reproducer

Three lines, reduced from the failing case by bisecting the *input*:

```cpp
class A { public: virtual int f() { return 0; } };
class B : public A { public: virtual int g() { return 1; } };
int main() { B b; return b.g(); }
```

A derived class that **adds** a virtual, and a call to it. Declaring it without
calling it is fine. `-ast` and `-layout` are byte-identical under both builds;
`-ir` and `-bc` crash under the cxx1 build alone.

## What the bisect says

`tools/` has no script for this yet — it was done by hand and is worth keeping:

1. Build Compiler++ twice, once with cxx1 and once with
   `clang++ -std=c++11 -I <compilerpp> -I include`. **Both must use cxx1's own
   headers**, or the two builds have different `std::string` and nothing links.
2. Link fifteen clang objects with one cxx1 object, sixteen times.

Every mix links now, which took the `St` abbreviation, the specialization
namespace and the enumeration name to achieve - before those, 3 of 16 mixed.
**Exactly one mix crashes: `Lower1.o`.**

## Where it crashes

cxx1's frames are not walkable by lldb, but cxx1 keeps a frame pointer, so the
chain can be read by hand: `memory read -f A -c 2 $x29` gives
`[x29] = caller's x29` and `[x29+8] = return address`.

    lowerBlock  (Lower.cpp, clang-built)
      lowerStmt (Lower.cpp:541:28, clang-built)
        __dynamic_cast
          dyn_cast_get_derived_info   <- EXC_BAD_ACCESS

The object being cast reads `3, 0, 3, 3` — small integers, no vptr. It is not a
corrupted object, it is **not an object at all**: something handed that call a
pointer into the wrong memory. `Lower.cpp:541` is

    v = convert(v, typeOf(rs->expr), currentReturnType, rs->line);

and the first time that line is reached `rs->expr` is a valid `cc::NumberExpr *`,
so the bad one is a later hit.

## What has been ruled out, and how

* **Class layout.** `ClassDecl`, `MethodDecl` and `FieldDecl` have identical
  `sizeof` and identical member offsets under both compilers - measured by
  compiling the same probe with each and linking it against that build's
  objects. So it is not the two compilers disagreeing about a record.
* **Nine isolated shapes**, each written to match what the code does and each
  agreeing with clang: a derived class adding virtuals; implicit constructors
  throughout; `dynamic_cast` through a `map` of `vector`s of base pointers; a
  const-map `find`/`end` pair; a member whose own member is a `std::string`; a
  by-value class returned through a pointer call and assigned to a member; the
  same across two translation units; a user-written constructor that omits a
  string member; and a qualified base call whose base `dynamic_cast`s its
  argument.

## The lesson worth carrying

The probes cost hours and found nothing. What found the *previous* bug in this
same file - and what narrowed this one from sixteen files to one - was the
differential: same sources, two compilers, diff the behaviour. **Reach for the
differential before reasoning about shapes.** A probe is a hypothesis about a
program of sixteen files; the bisect is an answer.
