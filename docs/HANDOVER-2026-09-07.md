## The virtual-base work

`class D : virtual public V` was not implemented at the start of the day. It now
is, up to a line that is drawn below.

**Done, and matching clang byte for byte:**

- **Layout.** A virtual base is laid down after the most-derived class's own
  non-virtual data, not inside the base that named it. `Type` grew
  `BaseSpec::isVirtual`, `nvDataSize_` (the size without the virtual bases) and
  `hasVirtualBase()`; a base contributes only its `nvDataSize()` to the class
  built on it. `setNvDataSize` is set **only when the class has a virtual
  base** - unconditionally, it stops POD tail padding being reused and
  `base-tail-padding` fails.
- **A vptr where there is no virtual function.** `hasVptr()` is
  `polymorphic() || hasVirtualBase()`: a class needs the pointer to find the
  base at all. Five sites ask it now rather than `polymorphic()` - the layout,
  `declareImplicitSpecials`, `synthesizeDefaultCtor`, the secondary-vptr store,
  and the vptr store in a **written** constructor or destructor.
- **The vtable.** `vbase_offset` entries in reverse order before offset-to-top,
  and a secondary table with its own `vbase_offset` for each base that has a
  vptr of its own. `Diamond`'s table reads `16 0 0 8 -8 0`, which is clang's.
- **Reading a member of a virtual base**, `virtualBaseMember()` in
  ParserClass.cpp: `*(T *)((char *)&o + *(long long *)(*(char **)&o + back) +
  within)`. Both member-access sites call it, **guarded on
  `m->inVirtualBase != nullptr` before the object expression is moved** - the
  guard is the whole fix, and testing it after the move cost 171 failures once.
- **Converting a pointer to a virtual base** reads the offset out of the vtable
  rather than adding a constant (ParserOverload.cpp).
- **A written constructor or destructor** of a class with a virtual base
  reaches that base by the **constant** offset, not through the vtable: the
  class laying the base down knows where it put it, and the vptr the walk would
  follow is stored after the base is built, so the vtable cannot be read there
  yet. This is the last change of the day.

`~/Documents/Claude/SparseMatrix/inheritance.cpp` runs identically to clang, and
so does a diamond whose classes have written constructors *as long as no class
is built as a base*:

```
struct V { V(); ~V(); };  struct D1 : virtual public V { D1(); ~D1(); };
D1 x;          cxx1: +V +D1 -D1 -V         clang: +V +D1 -D1 -V
```

**Not done, and this is the next thing.** The complete-object constructor and
the base constructor are the same symbol here - `C1` and `C2` are emitted as two
names on one body, and `D1` and `D2` likewise. That is right until a virtual
base exists, and then it is not: the base subobject must **not** build the
virtual base, because the most-derived class already did.

```
struct Dia : public D1, public D2 { Dia(); ~Dia(); };
Dia d;   clang: +V +D1 +D2 +Dia -Dia -D2 -D1 -V
         cxx1:  +V +D1 +V +D2 +V +Dia -Dia -V -D2 -V -D1 -V
```

V is built three times and destroyed three times. **The fix is to split C1 from
C2** for a class with a virtual base: C2 skips the virtual bases and C1 builds
them and then calls C2 - and a derived class calls the base's C2, which the
base-call loop in ParserTopLevel.cpp already names. After that come the VTT
(`__ZTT`) and the construction vtables (`__ZTC`), which are what makes a base's
constructor see the right vtable while it runs; nothing needs them until a
virtual function is called from inside one.

**Nothing of any of this was committed before the split was attempted** - check
`git log` for what actually landed.

## Working from the Windows PC

The tree is `git@github.com:Ghulamrs/Compiler-Cpp.git`, branch
`vector-exercise`. Read `CLAUDE.md` first; it opens with "Reading this tree".

**What the Windows box has, measured today:**

| | |
| --- | --- |
| `git` | `C:\Program Files\Git\cmd\git.exe`, on PATH |
| `cl` | VS 2022 Community, reached through `msvc\build.cmd` (not on a plain PATH) |
| `ssh` | `C:\Windows\System32\OpenSSH\ssh.exe`, **no keys in `%USERPROFILE%\.ssh`** |
| `python` | the Microsoft Store stub only |
| `bash` | not on PATH (Git ships one at `C:\Program Files\Git\bin\bash.exe`) |
| `clang` | **absent** |

`C:\cxx1\verify` is where `tools/verify-three` unpacks the tree it ships from
the Mac; it is a staging area, not a checkout. `C:\work` is the older
scratch tree. A checkout of the repo is a new directory.

**What changes if the work moves there, and it is not nothing:**

1. **The oracle changes.** Three of the four suites - `tests/run.sh`,
   `names.sh`, `overload.sh` - are shell and two of them compare against
   `clang++`. On Windows the differential oracle is `cl`, through
   `msvc\run-cases.cmd`, and `cl` is the right oracle for the Microsoft ABI
   anyway. But **a Windows-only loop cannot see an Itanium regression**, and
   most of this compiler is Itanium.
2. **`tools/verify-three` runs from the Mac.** It tars the working tree and
   ships it to the Linux box and the Windows box over ssh. For Windows to drive
   the round instead, that box needs a key to the Linux instance and to the
   Mac, and the script needs a `cmd`-side equivalent. Neither exists today.
3. **Git Bash makes the suites runnable** - put `C:\Program Files\Git\bin` on
   PATH - but without `clang` the two comparing suites have nothing to compare
   with. `run.sh` alone works: it reads `.expected` files.

**The honest recommendation:** edit and build on Windows, and keep the Mac in
the loop for the Itanium half until either `clang` is installed on the Windows
box (LLVM ships a Windows build, and that would let `names.sh` and
`overload.sh` run there) or `verify-three` is given a Windows driver. The
standing rule in CLAUDE.md - Mac, Linux and Windows all green before a commit
counts - does not change because the keyboard moved.
