Addendum, 1 September 2026: all nineteen confirmed findings are closed, each with a fix and a test, each verified on the three machines.

The findings below are left exactly as written. This page is the record of what was true at 29f8dfb, and correcting it as things are fixed would destroy the only thing a dated audit is good for. Live status is in CLAUDE.md under “The audit of 2026-09-01”. The two suspected items are still open and still suspected.

The suite grew from 201 run cases to 223 and from 292 emissions to 348 along the way, and gained one thing it did not have: a check that compiles one side of a call with cl and the other with cxx1, which is the only way the calling-convention finding could be proved. Four fixes were wrong on the first attempt and the tests said so — two of them only on the box that owns the target.

The suites are green and the compiler is not. That gap is the finding — everything below it is detail.

A four-suite run at this commit reports 201 cases, 295 emissions, 99 linkage-name comparisons and 26 overload comparisons, passing on the Mac, the Linux box and the Windows box. Underneath that, an ordinary program that returns a by-value parameter destroys one object twice; a class with a move constructor is copied bytewise instead of moved; a struct passed by value loses its tail bytes on two of three targets; and the compiler itself reads freed memory while parsing a default argument.

02Silent wrong answers

Programs that compile, link and run, and produce something other than what C++11 says. These are ranked first because nothing in the build tells you they happened.

S-01 Returning a by-value parameter elides a copy the standard forbids, and one object is destroyed twice Double freeReproduced
struct T { T(); T(const T &o); ~T(); }; // each prints c / C / d T pass(T t) { return t; } int main() { T b; { T d = pass(b); } }
clang -std=c++11cCCddd
cxx1cCddd

Two objects are constructed and three are destroyed. [class.copy]/31 excludes function parameters from copy elision precisely because the caller destroys the argument; the return path treats any local Var as elidable, and a parameter is a local. For any class that owns memory this is a double free.

src/parser/ParserStmt.cpp:1368 — v->isLocal() is true for parameters

S-02 A move-only class is copied bytewise, and its deleted copy constructor is accepted Double freeReproduced
struct S { int v; S() { v = 5; } S(S &&o) { v = o.v; o.v = 0; } }; S a; S b(static_cast<S &&>(a)); printf("%d %d", b.v, a.v); S c = a; // ill-formed: copy is deleted
clang -std=c++115 0 rejects `S c = a;`
cxx15 5 accepts, copies bytes

The move constructor never runs: the declaration path falls through to the byte copy inherited from the C compiler. [class.copy]/7 deletes the implicit copy when a move constructor is declared — cxx1 merely never declares one, so the byte path answers instead. With a pointer member the reviewer's version double-freed and trapped. Rung 7.4 is recorded in CLAUDE.md as landed, and the by-value-argument half of it genuinely is; the declaration half is not.

Root: implicit-copy suppression is an absence, not a deletion — the struct-assignment path predates it

S-03 An override of a non-first base, written without the virtual keyword, dispatches statically Wrong callReproduced
struct A { virtual int fa() { return 1; } }; struct B { virtual int fb() { return 2; } }; struct D : A, B { int fb() { return 22; } }; // no `virtual` written int main() { D d; B *pb = &d; return pb->fb(); }
clang -std=c++1122
cxx12

The implicit-virtual slot search scans only the primary base's vtable, which is seeded from base 0 alone — so an override of a second base is never recognised as one, is declared non-virtual, and the secondary vtable keeps the base's entry. Writing virtual explicitly fixes it, which is why every test case passes: they all write it. CLAUDE.md states the opposite rule — "finding a base's slot is what makes a function virtual, not the keyword".

src/parser/ParserClass.cpp:1904 and src/parser/ParserType.cpp:272 (bi == 0)

S-04 By-value aggregates lose their tail bytes on both Itanium targets Data lossReproduced
struct T3 { char c[3]; }; struct T6 { char c[6]; }; int use3(T3 s); int use6(T6 s); // sum the bytes use3({1,2,4}), use6({1,2,3,4,5,6})
clang -std=c++117 21
cxx1 (arm64-darwin)3 12

Any aggregate whose size mod 8 is 3, 5, 6 or 7 is spilled with the single largest store that fits rather than a composed 4+2+1 — a 3-byte tail stores 2 bytes, a 6-byte tail stores 4. It affects arm64-darwin and x86_64-linux, in argument spills, call-result stores and returns. x86_64-windows escapes it because non-power-of-2 aggregates go by reference there and its copy helper loops. That is the house bug class exactly: one target right, two silently wrong.

src/backend/Arm64Darwin.cpp:146, src/backend/X86_64Linux.cpp:1443, 1465, 913, 1010, 1174

S-05 Tail padding of a POD base is reused, so sizeof disagrees with every oracle on every target LayoutReproduced
struct TP { int a; char b; }; struct TD : TP { char c; }; sizeof(TP), sizeof(TD)
clang (all three)8 12
cxx1 (all three)8 8

Every base is laid at the base's unpadded size. Itanium reuses tail padding only for non-POD bases — for a POD base, dsize equals sizeof — and MSVC never reuses it at all. Assigning through a base pointer then overwrites the derived member. The codebase knows the reuse rule deliberately; what is missing is the POD carve-out.

src/parser/ParserType.cpp:758, 270; also ParserClass.cpp:1564

S-06 Deleting a null pointer runs the destructor CrashReproduced
struct T { int v; ~T() { v = 0; } }; int main() { T *z = 0; delete z; return 0; }
clang -std=c++11no-op, rc=0
cxx1SIGSEGV, rc=139

[expr.delete]/2: deleting a null pointer has no effect. The delete-expression emits the destructor call — or the vtable load, for a virtual destructor — with no null guard at all. delete p; on a pointer that may be null is ordinary code.

src/parser/ParserExpr.cpp:2932 onwards

S-07 A virtual call inside a base destructor reaches the derived override Wrong callReproduced
struct A { virtual int f() { return 1; } virtual ~A() { print(f()); } }; struct B : A { int f() { return 2; } ~B() {} }; int main() { B b; }
clang -std=c++111
cxx12

Constructors re-store the vptr as each level runs, and that direction is correct. Destructors never store it, so during ~A the object still claims to be a B and a derived override runs against a partially destroyed object.

src/parser/ParserClass.cpp:147 — the vptr helper the destructor path never calls

S-08 Comparisons yield int, and hex literals skip unsigned int Type systemReproduced
sizeof(1 == 1) // bool in C++, int here sizeof(0x80000000) // [lex.icon]: hex goes int -> unsigned int -> long 0xFFFFFFFF == -1 // true in C++11
clang -std=c++111 4 true
cxx14 8 false

Two independent faults with the same reach. Every comparison and logical operator stamps int on its result, so overloading on bool versus int picks the wrong function and auto b = (1==2) gives an int. Separately, one fits() ladder serves every radix, so hex and octal literals never pass through unsigned int — which changes the signedness of comparisons written against masks.

ParserExpr.cpp:230, 2391, ParserOperator.cpp:257, 273; literals at ParserExpr.cpp:1360

clang -std=c++110

[dcl.init]/7: P() on a class with no user-provided constructor zero-initialises. cxx1 hands over whatever was on the stack, reproducibly and differently per call site. Not recorded in CONFORMANCE.md, which exists for exactly this category.

S-10 A default argument leaks from one function onto the next one declared Wrong callReproduced
int g(int a); int g(int a = 5) { return a; } // legal C++: adds a default on redeclaration int h(int b) { return b * 10; } int main() { return h(); } // h takes no default — this is an error
clang -std=c++11rejects h()
cxx150

The redeclaration path clears the pending noexcept but neither stores nor clears the pending default arguments, so the next function declared inherits them. g's default is dropped where it belongs and re-read as h's token stream where it does not.

src/parser/ParserClass.cpp:2058 (returns without clearing pendingDefaults_)

Four more in this class are reviewer-confirmed and not re-run here: goto past an initialisation is accepted and then destroys a never-constructed object; narrowing in list-initialisation is silently truncated (char c = {300} gives 44); an lvalue against f(int) and f(const int &) is ambiguous in C++11 and cxx1 quietly picks one; and const S s; for a POD with no user constructor is accepted where C++11 requires an initialiser.

03ABI divergence and code generation

Where cxx1 is self-consistent but disagrees with the platform — visible only when its objects meet someone else's, which is the whole premise of a compiler that ships no standard library.

A-01 On x86_64-windows, this and the hidden return pointer are passed in the wrong order ABI breakReviewer-confirmed

For a member function returning a struct through the hidden pointer, cl and clang-msvc pass this in RCX and the sret pointer in RDX. cxx1 reserves integer slot 0 for sret ahead of every parameter including this, so it passes them the other way round — on both sides of the call, which is why nothing inside cxx1 notices. Any link against cl-compiled code is silently wrong. The Itanium targets are correct.

src/backend/X86_64Linux.cpp:838, 977, 1371 — needs the Microsoft order when abi_.positional

A-02 A vtable references an implicit destructor that is never emitted, and the program does not link Link failureReproduced
struct B { virtual ~B(); }; B::~B() {} struct D : B { }; // implicit ~D int main() { B *p = new D; delete p; return 0; }
clang -std=c++11links, runs
cxx1symbol not found

D's vtable points at ~D's two forms, but nothing in the source names ~D, so the used flag never fires and no body is emitted. A vtable slot is a use; it is not counted as one. Single translation unit, whole-program compile — this is rung 4 failing at link.

Emission gap rather than an ABI question; found on all three targets

04Defects in the C++14 source

The compiler's own correctness, as opposed to the language it accepts. All four suites pass under an ASan+UBSan build with no reports, so each of these lives just off the tested paths.

C-01 A Signature & into functions_ dangles across a default-argument re-parse Use after freeReproduced
template <class T> T id(T v) { return v; } int f(int a, int b = id(7)) { return a + b; } int main() { return f(1) == 8 ? 0 : 1; }
clang -std=c++11compiles, rc=0
cxx1'' has no default for parameter 3

Applying a default argument re-parses its tokens. If that expression instantiates a function template or builds a lambda, functions_ reallocates and the reference the caller still holds is freed memory — the diagnostic above is reading it, which is why it names an empty function and a third parameter that does not exist. The reviewer's ASan build reports heap-use-after-free on the same input. The repo fixed this identical bug once, at one site, and wrote down the lesson; roughly ten call sites still hold the reference.

Read at ParserOverload.cpp:521, freed at ParserTemplate.cpp:796. Sites: ParserExpr.cpp:118, 160, 663, 1200, 1428, 1563, 2877, 3106, ParserOperator.cpp:463, ParserClass.cpp:17. Fix: take the Signature by value.

C-02 An array's size overflows a signed int, and the assembler is handed a negative length Invalid outputReproduced
static int a[600000000];
clang.zero 2400000000
cxx1.zero -1894967296

Sizes are computed in int. UBSan names it directly; the shipped -O2 binary emits the negative literal without complaint. A length above 231 truncates in the cast as well.

src/Type.cpp:24 — compute in long long, and diagnose an over-large object where it is declared

C-03 The host's long double decides the target's x87 constants Host-dependentReviewer-confirmed

Literals are parsed with strtold into a host long double and the 80-bit encoding is derived from it. On this arm64 Mac, where long double is a double, long double x = 0.1L; emitted for x86_64-linux gets significand 0xCCCCCCCCCCCCD000 where the correct value is 0xCCCCCCCCCCCCCCCD. A Linux-built cxx1 emits it exactly. The same source therefore produces different objects depending on which machine built the compiler — cross-target divergence relocated into the front end, where three-box verification cannot see it, because each box checks its own build.

src/Lexer.cpp:209, src/Type.cpp:332, and foldDouble in ParserInit.cpp

Array lengths and the preprocessor's #if evaluator use long, which is 32-bit under cl. char a[0x100000001] truncates to char a[1] on the Windows-built compiler and is accepted at full width on the other two. Surrounding code already uses long long.

06Why a green suite proves less than it looks

The mutation pass answers this with evidence: plant a deliberate bug in a copy of the tree, rebuild, and see whether make test notices. Nine were planted. Four survived every suite.

Each survivor was proved a real bug rather than an equivalent mutant. The unsigned-division one prints 18446744073709551615 where clang prints 9223372036854775807 — wrong code on the host target, with all four suites green, because no case in the tree performs runtime unsigned division. The Windows one leaves mov rbp, rax visible in the emitted assembly; emit.sh checks that the compiler exited 0 and a file appeared, so every Windows function can be broken and the suite stays green.

Two more results matter as much as the survivors. The mangling mutant was caught by names.sh alone and the ranking mutant by overload.sh alone — and both of those suites exit 0 when clang is absent, which is the state of the Linux box. A green make test there tested neither the ABI nor overload resolution and said nothing about it.

  • Every test writes virtual on its overrides, which is why S-03 has never fired. The suite tests the language as the author writes it, not as the standard permits it.
  • No case counts constructors and destructors — deliberately, because elision is permitted and the oracles differ. Sound as a decision, and exactly why S-01 and S-02 are invisible: a double destruction looks like nothing unless someone counts.
  • run.sh ignores the test binary's exit status — only stdout is diffed, so a case that prints its expected output and then crashes in a late destructor passes. Several cases end in return <expr> as though it were checked.
  • The 425-file C corpus is referenced only from CLAUDE.md. No script in the tree runs it, which makes it indistinguishable from coverage while contributing none.
  • Some invariants hang on a single case, and some .error files are byte-identical to each other, so a diagnostic that moves to the wrong construct with similar wording stays green.
  • Three-box verification checks three builds of the compiler, not one compiler on three machines — C-03 produces different output per build host and passes on all three.

07What I would fix, in this order

  1. The two double-frees, S-01 and S-02.

    They are the only findings that corrupt a correct program's memory, they are both in the copy/move path that rung 7.4 claims to have finished, and the second one also accepts a program C++11 rejects. Add cases that count constructors and destructors — the reason not to count them applies to elision, not to the total.

  2. C-01, the use-after-free in the compiler.

    One-line fix per site: take the Signature by value. The repo already learned this lesson once; finishing it is cheaper than meeting it a third time.

  3. S-03 and S-05 — the two that make the object model quietly wrong.

    A keyword-less override of a second base, and POD base padding. Both are layout- or dispatch-level, both affect all targets, and both are the kind of thing another compiler's object would disagree with.

  4. S-04 and A-04, the target-specific codegen faults.

    Tail bytes and the unsigned conversion. Neither can be caught by any suite that runs only on the host, so a way of running the other two targets — even a slow emulator on the Linux box — buys more than the fixes do.

  5. Then the type-system corrections, S-08 and S-09.

    bool results, the hex literal ladder, and value-initialisation. Each is small on its own and each changes what overload resolution picks, so they are worth doing together and re-running the overload suite after.

  6. Last, the record.

    Six stale claims and two diagnostic patterns. Cheap, and the project's whole method depends on CLAUDE.md being true — every finding above was found faster because the rest of it is.

08What held

An audit that only lists faults misrepresents the thing it audited. These were probed hard and came back clean.

  • The C++11 boundary. Fifteen C++14 forms tested; every one refused. The constexpr member function is implicitly const, which is C++11's rule and not C++14's, and cxx1 answers C++11 on both halves — accepting the call C++14's clang refuses and refusing the mutation it accepts.
  • Name mangling, both ABIs. Namespaces, nested classes, every fundamental type, function and member pointers, operators, constructors and destructors, template functions and classes, back-reference saturation past ten types, vtable symbols — matched against clang for all three ABIs.
  • Calling conventions, in the large. SysV eightbyte classification including mixed lanes, arm64 HFAs and their spill, Apple's packed stack arguments, variadics on all three targets, the 32-byte shadow space and 16-byte call alignment on Windows.
  • Cross-compiler interop on Darwin for struct passing and returns at 4–24 bytes, non-trivial classes, vtables built by one compiler and read through the other, and __cxa_ throw/catch of fundamental types in both directions.
  • Arithmetic. Integer promotions, the usual arithmetic conversions, shifts, ternary typing, NaN comparison semantics on all three ISAs, bitfield runtime semantics including 40-bit fields.
  • The C++14 source's discipline, where it is deliberate: no C++17-isms, every dynamic_cast guarded, every token-skip loop bounded, constant folding written with care around overflow and division by zero, and RAII unbinding in the template replay paths — which is what makes C-01's sites stand out as stragglers rather than as the norm.
