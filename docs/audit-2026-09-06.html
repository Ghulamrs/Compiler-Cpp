What was asked, and why it worked this time

Fable 5 and 5.1 had reviewed this tree repeatedly and returned nothing actionable. The difference here is the brief, not the reviewer. Each of the three was given a named defect shape drawn from bugs this compiler had actually shipped, a demand that every claim arrive as a program with both compilers' real output, and an instruction to report negative results honestly. A brief that says “review this compiler” returns prose. A brief that demands a failing program returns either a bug or a clean bill, and both are worth having.

The target was stated as exactly ISO C++11 — no overstepping and no understepping, so both directions count as defects: code C++11 requires that cxx1 refuses or miscompiles, and code C++11 forbids that cxx1 accepts. Reviewers were warned that the oracle is not the standard: clang under -std=c++11 back-ports some C++14 relaxations, and where the two disagree the ISO text governs. No finding below rests on a back-ported relaxation.

Verified by hand

These nine were re-run against the same binary rather than taken on a reviewer's word, because an agent's report is a hypothesis until it is reproduced. All nine reproduce. Programs are shown as run.

V-01 A user-written destructor never destroys the class's data members Silent leakVerified
struct P { int n; P() : n(5) {} ~P() { printf("-%d ", n); } }; struct D { P x; ~D() { printf("~D "); } }; int main() { { D d; } printf("\n"); }
clang -std=c++11~D -5
cxx1~D

[class.dtor]/8: after the body has run, a destructor calls the destructors for the class's non-static data members, then its bases. The implicit destructor does this; a written one does not — the same implicit-path-only shape as the constructor bug already recorded in CLAUDE.md under “A base's members were built twice”. Any class with ~C() { } and a std::string member leaks it. No base, no mem-initialiser and no inheritance are needed to reach it.

Root: R2 — the member and base walk lives only in the synthesised destructor

V-02 A data member is hidden by a global of the same name Silent wrong valueVerified
int k = 10; struct S { int k; S() : k(3) {} int get() { return k; } }; int main() { S s; printf("%d\n", s.get()); }
clang -std=c++113
cxx110

[class.mfct.non-static]/3 and [basic.lookup.unqual]/8: inside a member function an unqualified name that names a member is transformed to (*this).name. The member path is consulted only when findGlobal(name) == nullptr, so any class whose member shares a name with any global anywhere in the program silently reads the wrong object. It is also why a captured [k] reads the global rather than the member.

V-03 An enumerator hides a local variable and a function parameter Silent wrong valueVerified

V-05 A class captured by value is copied bytewise, and the closure's copy is never destroyed Silent leakVerified
struct T { int *p; T(int x) : p(new int(x)) { printf("ctor "); } T(const T &o) : p(new int(*o.p)) { printf("copy "); } ~T() { printf("dtor "); } }; int main() { T a(7); auto f = [a]() { return *a.p; }; printf("%d ", f()); }
clang -std=c++11ctor copy 7 dtor dtor
cxx1ctor 7 dtor

The copy constructor never runs and the closure's member is never destroyed — two objects exist where clang has two and destroys two, and here the second was never built as an object at all. For a class that owns memory the two copies share a pointer, so the surviving one is a use-after-free waiting for the other's destructor.

Root: R3

V-06 A lambda's return-type deduction leaks alive_, and a destructor runs on a slot nothing constructed SilentVerified
struct S { int v; S(int n) : v(n) { printf("ctor %d\n", n); } ~S() { printf("dtor %d\n", v); } }; int main() { auto f = []() { S s(3); return s.v; }; int r = f(); printf("r=%d\n", r); }
clang -std=c++11ctor 3 / dtor 3 / r=3
cxx1ctor 3 / dtor 3 / r=3 / dtor 1

This is the original alive_ bug, one door over. deduceLambdaReturn parses the statements before the lambda's return for real, in the enclosing function, and restores only locals_, scopeStarts_ and at_. The entry pushed onto alive_ is never popped, survives into the enclosing function, and main's exit destroys an object that was never constructed. [class.dtor]/11.

Review A — per-function state across a nested parse

The axis: cxx1 re-enters parsing from a saved token index in eight places, each with its own hand-written list of state to save and restore, each written separately. That is how the shipped alive_ bug happened. The reviewer classified every per-function field of class Parser as saved, provably-safe, or unsafe, and reproduced every member of the third class.

Beyond V-01, V-04 and V-05: a member function taking T&& given a call's prvalue is handed a different object from the one destroyed (a double free with an owning class); a lambda whose body returns a class from a call runs a destructor on an unbuilt slot, and aborts for [](const std::string &s) { return s + "!"; }; a two-dimensional array member of class type has only its first row constructed; any polymorphic class template emits an unassemblable _ZTS symbol spelled from the tag rather than the mangled template-id.

Fourteen shapes of ordinary valid code are refused without being named in EXCLUSIONS.md. Two deserve singling out: parenthesised direct-init of a scalar — int z(5); — on which the repository's own <utility> depends, so std::swap on two ints fails inside the header; and [=]/[&] inside a member function not implicitly capturing this.

Of the 27 over-acceptances, three are already in CONFORMANCE.md. The rest are not, and the ones a real program reaches are: a class with a reference or const member accepting default construction ([class.ctor]/5 deletes it); a duplicate data member; a constructor with a return type; auto a = 1, b = 2.0;; a lambda with inconsistent return types; operator+(int, int) at namespace scope; an explicit operator bool used in copy-initialisation; and a virtual function “overridden” with an incompatible return type. Every C++14 form probed — 0b101, 1'000, generic lambdas, return-type deduction, init-captures, NSDMI aggregates, [[deprecated]], variable templates, decltype(auto) — is correctly refused.

The finding about the method, not the compiler

Compiler++ compiles under cxx1 and matches a clang build on all 200 comparisons, on all three targets. It does so under a compiler that leaks every data member of every class with a written destructor (V-01). It passes because a leak does not change what reaches stdout.

That is not a gap in the corpus, which can be widened; it is a gap in the oracle. Output comparison — the method this entire tree rests on, from run.sh through verify-three to the 200-case Compiler++ differential — cannot see a leak, a double free that happens after the last print, a destructor running on an unbuilt slot, or any corruption that does not reach the output before the program ends. Four suites were green on three machines throughout everything above.

CLAUDE.md already prescribes the remedy for one case and does not generalise it: return-copy-balance.cpp and move-only.cpp count live objects rather than constructor calls, precisely because elision makes counts meaningless while a leak or a double free moves the balance and nothing else does. V-01, V-05, and review B's constructor-throw and mem-initialiser leaks are all invisible to output and all visible to a live-object count. Fixing the oracle should come before fixing the compiler, or the suites will keep certifying this class of defect as green.

Negative results

Recorded because a review that reports only hits cannot be sized. Review A tried and cleared: pendingTemps_ and localTypes_ through the deduction parse, a default argument shadowed by a caller's local, a lambda in a default argument called from two functions, a lambda in a member initialiser with two constructors, inlineOwner_ through a nested-class replay, and a static local in an ordinary inline member. Review B cleared roughly twenty-five shapes including [class.protected] through a base-typed object, const propagation through all three member paths, private conversion functions and operators from outside, ten scope-exit shapes with identical destructor traces, and by-value copies for every call form but the mem-initialiser. Review C's live-balance comparisons agreed for exceptions through destructible frames, virtual calls in constructors and destructors, multiple-inheritance construction order, operator overloading with temporaries, ?: and &&/|| temporaries, member templates, variadics, SFINAE, and all eight header programs.

One harness trap is worth passing on: -w silently disables clang's -pedantic-errors diagnostics, which mis-scored six C++14 forms as accepted until it was removed and everything re-run.
